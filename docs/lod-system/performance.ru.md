# Как доказать, что новая LOD-система не тяжелее Voxy

Это протокол будущей приёмки, а не результаты ещё не проведённого замера. Текущие результаты — только [синтетический benchmark](../hybrid-wip/geometry-benchmark.ru.md) и предыдущие игровые проверки WIP на llvmpipe.

## Что сравниваем

A: исходный кубический backend Fragment Vision/Voxy с текущим общим светом Fragment Render, без HybridTerrain.

B: собственный backend из заранее подготовленного пакета, без исходных geometry draw Voxy. Смена формы рельефа и растительности — ожидаемое художественное отличие; видимая дальность, существенные объекты и требования к качеству сохраняются.

Отдельное сравнение с upstream Voxy другой версии Minecraft/loader/шейдера не подменяет A/B. Если понадобится, оно имеет отдельную таблицу и ограничения. «Быстрее Voxy» в итоговом сообщении должно указывать конкретный baseline.

Предгенерация карты доступна обоим. У A заранее импортированы все чанки, нет world generation в замере. Warm render сравнивается с прогретым A, а не с первым импортом Voxy. Преимущество B в offline bake допустимо отдельно измерить как ускорение cold-start/streaming; цена bake и размер пакета указываются.

## Одинаковые условия

- Версии Minecraft, Java, Sodium, модов, пака и драйвера; hardware ID, CPU/GPU/RAM/VRAM.
- Карта/ревизия, координаты камеры и маршрут, погода и время; одинаковые FOV, разрешение, AA и preset Render.
- Native 6/8/12 чанков, LOD сначала 512 блоков, затем 1024/2048 и целевая дальность карты. Не сравнивать более короткую дальность B с большей A.
- Сопоставимый shading: те же sun/sky/cloud shadows, одинаковая атмосфера. Дополнительную дальнюю shadow-map/High функцию измерять отдельной дельтой, а не прятать в геометрическом A/B.
- Отключённые VSync/FPS limiter для замера throughput; затем отдельная проверка под целевым лимитом для плавности/потребления. Стабильные настройки энергопитания, без фоновой bake-нагрузки.
- Камера, скриншоты и warm-up фиксированы. Порядок A/B/A либо чередование серий для снижения температурного и cache bias.

## Метрики

| Область | Что записывать |
|---|---|
| Полный кадр | CPU frame time и GPU frame time, median/p95/p99; FPS только производная |
| LOD GPU | selection/culling, opaque terrain, canopy/cutout, water, compose, дополнительные shadows |
| LOD CPU | main/render thread, worker core-ms, queue wait; build wall time отдельно |
| Геометрия | submitted triangles/vertices/quads по типам и LOD, draw count, culled nodes, parent/child overlap |
| Пиксельная цена | covered pixels, overdraw/alpha workload, стоимость fragment shader; где возможно GPU pipeline counters |
| Память | resident geometry/textures/metadata/staging, old+new при swap, JVM heap и native/direct memory, process RSS |
| Загрузка | disk bytes, decode CPU time, upload bytes/frame, время до приемлемого мира после teleport/cold start |
| Изменения | edit→native, edit→visible LOD, edit→all affected parents, peak pending bytes и worst burst |
| Офлайн | bake wall/core time, peak RAM, размер пакета/регион и материалов, повторный incremental bake |

GPU queries читать асинхронно через несколько кадров. Не использовать `glFinish` каждый кадр игрового теста: это меняет поведение pipeline. Записывать только необходимую диагностику, отдельно оценить её overhead. Submitted triangles считать **для всех** relevant draws, включая transitions/shadows/fallback; не путать подготовленные индексы со реально отправленными в кадре.

Рабочий GPU budget — реальная занятая/зарезервированная память всех LOD ресурсов. «512 MiB разрешено в настройке» и «429 MiB мешей наблюдалось» — разные показатели. Не считать разгрузку Java heap доказательством разгрузки VRAM.

## Набор сцен

| Сцена | Что может сломаться |
|---|---|
| Ровная поляна | Voxy почти идеально объединяет грани; лишняя mesh-плотность видна сразу |
| Холмы земли/дёрна | Основная цель: гладкая форма и согласованные цвета |
| Снежная каменная гора | Гребни, материал снега, скальные стенки и silhouette error |
| Берег/река/водопад | Water depth, shoreline, отражения, полупрозрачность |
| Берёзовый/смешанный лес | Белые стволы, tint, нормали крон, mip/alpha и просветы |
| Плотный лес с bushy в native | Стоимость cutout, шум и переход на clean LOD crown |
| Пещера/арка/навес/мост | Объёмная структура, отсутствие заливки колонкой |
| Деревня и дом из stone/dirt | Нельзя сгладить постройку по natural-block tag |
| Большой вид сверху | Худший случай видимой площади, отсутствие полезного occlusion |
| Тонкие башни/ограды/модовые блоки | Protected details, fallback и материал |

Для основных сцен: статичный кадр, медленное движение через native/LOD и LOD/LOD границы, поворот камеры, быстрый полёт и teleport. Снимать лес, поляну, холмы и берег, а не только удобный вид моря. Освещение: день, тень дерева, закат, ночь, дождь. Диагностические виды: wireframe, LOD owner/level, material ID, untinted albedo, normals, sky/AO/sun visibility, UV/mip, depth. Затем обычный художественный кадр.

## Стресс изменений и сохранений

Копание траншеи на границе tile, башня выше исходного ландшафта, изменение берега, удаление кроны, рост дерева, свет факела, TNT/массовое редактирование. Проверить смену уровня во время пересборки, уход игрока далеко и возвращение, сохранение/перезапуск, отмену worker, выгрузку измерения.

Пакет: отсутствующая страница, неверный checksum, устаревшая версия pack, новые block IDs, откат сохранения и новая версия base-карты. Deleted/empty страницы не возвращаются из base через cache miss. Очередь остаётся ограниченной; устаревшие revisions не публикуются.

## Предварительные бюджеты и критерии приёмки

Числа ниже — стартовые проектные ограничения, **не измеренные гарантии**. Уточнить после baseline на целевой GPU.

1. На каждом обычном covered участке выбран ровно один LOD representation. Старый MDIC terrain draw в режиме B отсутствует. Debug-счётчик дублирования равен нулю вне явно ограниченных переходов.
2. На representative route целиться в не менее 10% уменьшения median **LOD GPU time**, чтобы выигрыш был больше мелкого шума. Полный кадр может улучшиться слабее, если доминируют native, трава или небо.
3. Full-frame median и p95/p99 не должны устойчиво ухудшаться относительно A сверх измеренного разброса. Начальная диагностическая граница 5% — повод расследовать, не разрешение незаметно ухудшить итог. Повторить достаточное число серий и показать разброс; не выбирать один лучший кадр.
4. Resident LOD RAM/VRAM в сопоставимых сценах не выше baseline A как целевая планка. Отдельно сравнить peak swap/streaming и disk package. Если новая геометрия меньше, а текстуры/visibility дороже, показывать общий результат.
5. Runtime uploads — начать с бюджета порядка 1–2 MiB/кадр и до 0.5 ms CPU scheduling на целевом устройстве; разделять крупные страницы, чтобы один upload не обходил лимит. Это параметры для подбора, а не доказанная переносимость на слабые GPU.
6. Pending decoded/mesh payload — фиксированный общий byte budget (кандидат 16 MiB) плюс отдельный ограниченный рабочий набор worker. Размер всех одновременно живых snapshots также входит в лимит. Число worker адаптировать к доступным CPU, не занимать их все.
7. Экранная ошибка геометрии — стартово около 1 px на первом дальнем уровне и до 2 px дальше при целевом разрешении; material/silhouette и quantization проверяются отдельно. Порог нельзя ослабить только ради хорошей цифры FPS без явного указания потери качества.
8. Обычная ходьба в неизменённой карте не вызывает mesh extraction из блоков. Native edits немедленны, дальняя замена имеет измеренную ограниченную задержку. Начальная цель для единичной небольшой правки — видимый LOD за ~0.5 s на целевой машине, фоновые предки/затенение отдельно; массовые правки имеют свой бюджет и результаты.
9. Изображение должно пройти художественную проверку: нет снежных стен вместо камня, кислотных LOD-полян, плоских светлых берёз, щелей и заметных туманных полос. Производительность ценой этих дефектов не считается успехом.

Если для сложной сцены нельзя одновременно выполнить бюджет и качество, записать ограничение и изменить алгоритм/представление. Нельзя утверждать «не тяжелее Voxy» по одному тесту холмов или по меньшему числу треугольников.

## Формат отчёта следующего прототипа

Версии/хэши и hardware; фиксированные настройки и сцены; A/B/A таблицы frame/LOD timings, memory, payload, edits; исходные серии измерений; чистые F2 кадры одинаковых мест; diagnostic images; список известных артефактов и невыполненных gates. Отдельно offline cost и optional High features. Не смешивать timings программного рендера с аппаратными.

В доступном сейчас окружении используется llvmpipe. Здесь можно проверять корректность геометрии, shader compilation, ограничения памяти, дублирование draws и поведение обновлений. Финальное доказательство GPU-выигрыша требует аппаратного запуска; документация и малый прототип могут быть подготовлены заранее.
